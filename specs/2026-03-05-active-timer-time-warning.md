# 1. Summary
在“正在计时”页面新增计时预警：限时1小时套餐仅在剩余10分钟时提醒一次；限时2小时套餐在2小时还剩10分钟提醒一次。提醒形式为电脑语音播报 + 网页弹窗，并支持桌号字段，播报内容包含“桌号 + 剩余时间”。

该能力用于减少前台漏提醒导致的超时沟通成本，提升门店现场运营稳定性。

# 2. Goals / Non-goals
## Goals
- G1：为 `limited1h` 计时单在剩余10分钟触发一次提醒（即开始后第50分钟）。
- G2：`limited1h` 关闭提醒后不再触发后续档位提醒（即不再于第110分钟提醒）。
- G3：为 `limited2h` 计时单在剩余10分钟触发一次提醒（即开始后第110分钟）。
- G4：提醒必须同时包含两种形式：语音播报 + 页面弹窗。
- G5：每个计时单仅按套餐触发一次提醒，页面刷新后不重复提醒。
- G6：仅对“正在计时（active）”且“限时套餐（limited1h/limited2h）”生效，不影响不限时套餐。
- G7：计时单支持维护桌号（如 A1、B3），提醒语音与弹窗均优先展示桌号。
- G8：提醒弹窗仅手动关闭，不自动关闭。
- G9：桌号格式固定为“桌+数字”（如 `桌1`、`桌12`）。
- G10：桌号在“正在计时”范围内必须唯一，不允许重复占用。
- G11：桌号必须在“开始计时”时选择/填写，未填写不得开始计时。

## Non-goals
- NG1：不改计费公式与结算金额计算逻辑。
- NG2：不新增后端定时任务或推送服务。
- NG3：不引入第三方依赖包。
- NG4：不改“计时结束/手动结算”的现有流程。
- NG5：不实现自动桌号编排（但需实现格式与唯一性校验）。

# 3. Current State & Constraints
- 当前状态（关键路径）：
  - 计时页：`frontend/src/views/ActiveTimers.vue`
  - 套餐选项：`frontend/src/utils/timerConsume.js`
  - 计费辅助：`frontend/src/utils/consumptionCalculator.js`
  - 计时后端：`backend/routes/active_timers.py`
- 现状：前端存在 `nowTimestamp` 周期刷新与 `limited1h/limited2h` 套餐信息，但尚无“剩余时间预警”的状态管理与提醒通道。
- 约束：
  - 运行环境为 Windows + PowerShell。
  - 不自动安装依赖，不修改 lock/dependency 文件。
  - 浏览器语音能力受系统与浏览器策略影响（首个播报可能受用户交互门槛限制）。

# 4. Requirements
## Functional Requirements
### P0
- P0-1：`limited1h` 在开始后 `50±1` 分钟触发“剩余10分钟”提醒。
- P0-2：`limited1h` 关闭提醒后不再触发后续提醒（即超过1小时继续计时也不再提醒）。
- P0-3：`limited2h` 在开始后 `110±1` 分钟触发“剩余10分钟”提醒。
- P0-4：提醒呈现为：
  - 语音：自动播报“桌号 + 剩余时长”关键信息（无桌号时降级为客户名 + 剩余时长）；
  - 弹窗：可见标题、桌号、客户、套餐、触发时间、确认关闭按钮。
- P0-5：关闭弹窗后将该计时单标记为“已提醒完成”，不再重复提醒。
- P0-6：同计时单只提醒一次（防抖与去重）。
- P0-7：新增计时单（开始计时）时必须填写桌号，未填写阻止提交并提示。
- P0-8：桌号输入必须匹配正则 `^桌[0-9]+$`，不匹配时阻止提交并提示。
- P0-9：新增/编辑计时单时，若桌号与其他 active 计时单重复，阻止提交并提示“桌号已占用”。

### P1
- P1-1：刷新页面后仍应记住“已提醒状态”，避免重复提醒（前端本地持久化，按计时单ID）。
- P1-2：语音播报失败时不影响弹窗提醒；应在控制台记录失败原因。
- P1-3：多计时单同时命中时按触发顺序逐条展示，避免弹窗互相覆盖。
- P1-4：桌号字段在列表、弹窗、播报文案保持一致来源（同一计时单主数据）。
- P1-5：桌号唯一性校验需区分“当前编辑对象”；编辑同一条记录保留原桌号不应误判冲突。

### P2
- P2-1：预留预警阈值配置能力（默认10分钟，本次可先常量化）。

## Non-functional Requirements
- NFR1：轮询/计时检查不应导致明显卡顿（同屏20条计时记录下交互流畅）。
- NFR2：提醒判断时间误差不超过1分钟（受页面ticker粒度影响）。
- NFR3：移动端与桌面端弹窗可读，关键按钮可点击。
- NFR4：不影响现有计时筛选、编辑、结算交互。
- NFR5：桌号录入不增加明显操作负担（新增/编辑表单仅新增一个轻量输入项）。
- NFR6：桌号校验反馈应在 100ms 内响应（前端本地校验）。

## Compatibility / Migration
- C1：历史计时单不迁移数据库；仅前端运行态判断提醒。
- C2：提醒去重缓存采用版本化 key（如 `active_timer_warning_v1`），便于后续升级清理。
- C3：历史计时单默认桌号为空，旧数据无需迁移即可兼容。
- C4：若历史 active 数据存在非“桌+数字”格式，允许显示但在编辑保存时按新规则校验。

# 5. Design
## Overall Approach
- 在 `ActiveTimers.vue` 基于现有 `ticker`（`nowTimestamp`）增加“预警引擎”：
  - 计算每条 active 计时单的已用分钟；
  - 根据套餐映射目标提醒点：
    - `limited1h` -> `[50]`
    - `limited2h` -> `[110]`
  - 命中目标点且未触发过时，写入“待提醒队列”；
  - 依次执行：语音播报 + 弹窗展示 + 标记已触发。
- 在计时数据结构中补充 `tableNo`（或 `table_no`）字段：
  - 新增计时时录入；
  - 编辑计时时可修改；
  - 提醒时优先使用桌号播报与展示。
- 在新增/编辑提交前执行两层校验：
  - 格式校验：`^桌[0-9]+$`
  - 唯一性校验：与当前 active 计时列表比对（排除自身）。
- 状态管理：
  - 内存态：当前会话已触发集合，避免高频重复；
  - 本地持久化：`localStorage` 记录 `timerId: reminded`，防刷新重复。

## Key Decisions
- D1：提醒逻辑放在前端页面层，复用现有计时刷新机制，改动范围最小。
- D2：使用“里程碑分钟点”而非“剩余时间倒计时对象”，实现更稳定、可扩展。
- D3：语音采用浏览器内置能力（`speechSynthesis`），失败时降级为仅弹窗。
- D4：提醒弹窗仅手动关闭，避免用户错过关键提示。
- D5：桌号唯一性先以前端实时校验拦截，同时后端接口需二次校验避免并发脏写。

## Alternatives
- 方案A（选用）：前端本地提醒（ticker + localStorage）。
  - 优点：无需后端改造，开发快，部署简单。
  - 缺点：浏览器标签页关闭时无法提醒。
- 方案B：后端定时任务 + WebSocket 推送。
  - 优点：可实现离页提醒与多端一致性。
  - 缺点：改造重，超出本次范围。

## Impact Scope
- `frontend/src/views/ActiveTimers.vue`（核心提醒逻辑与弹窗）
- `backend/routes/active_timers.py`（若当前接口未携带桌号则补充）
- `backend/models/models.py`（若需持久化桌号字段）
- 可选：`frontend/src/utils/dateTime.js`（若抽离分钟点计算工具）
- 可选：`frontend/src/utils/modalBackdrop.js`（若复用弹窗关闭行为）

# 6. Acceptance Criteria
- AC1：创建 `limited1h` 计时后，运行到约50分钟触发一次“剩余10分钟”语音+弹窗。
- AC2：同一 `limited1h` 计时关闭提醒后，即使继续运行到110分钟也不再提醒。
- AC3：创建 `limited2h` 计时后，仅在约110分钟触发一次提醒。
- AC4：手动关闭提醒后，不会再次弹出同计时单提醒。
- AC5：刷新页面后，已提醒计时单不会重复触发。
- AC6：语音不可用时仍有弹窗，且页面功能不中断。
- AC7：不限时套餐（工作日/周末不限时）不触发该预警。
- AC8：提醒语音内容包含桌号与剩余时间；桌号缺失时降级为客户名与剩余时间。
- AC9：提醒弹窗不会自动关闭，仅在用户点击关闭后消失。
- AC10：桌号格式非“桌+数字”时无法提交新增/编辑，并有明确错误提示。
- AC11：存在同名 active 桌号时无法提交新增/编辑，并有“桌号已占用”提示。
- AC12：开始计时时未填写桌号无法提交，并有“请选择桌号/请输入桌号”提示。

# 7. Validation Strategy
候选验证命令（PowerShell）：
```powershell
# 命令1：前端构建
cd frontend; npm run build
# 预期：build 成功，无 error

# 命令2：可选语法检查（如拆分了工具文件）
node --check frontend\src\views\ActiveTimers.vue
# 预期：无语法错误（若命令不支持 .vue 则仅执行构建）
```

手工验证步骤（重点）：
1. 进入“正在计时”，新增 `limited1h` 计时单。
2. 在新增表单填写桌号（如 `桌1`），启动计时。
3. 将系统时间推进或使用测试辅助使已用时长跨过 50 分钟，确认提醒触发，语音包含桌号 + 剩余时间。
4. 手动关闭弹窗后继续计时至 110 分钟，确认 `limited1h` 不再提醒。
5. 新增 `limited2h` 计时单并填写桌号，确认仅在 110 分钟附近触发一次。
6. 新增另一条 active 计时并填写相同桌号（`桌1`），应被阻止并提示占用。
7. 将桌号改为非法格式（如 `A1`），应被阻止并提示格式错误。
8. 尝试不填桌号直接开始计时，应被阻止并提示必填。
9. 刷新页面后检查同计时单不重复提醒。

# 8. Risks & Rollback
- 风险R1：浏览器语音播报被策略拦截。
  - 缓解：语音失败降级为弹窗；记录 console 告警。
- 风险R2：ticker 频率导致提醒点略偏移。
  - 缓解：使用区间命中（±1分钟）与去重标记。
- 风险R3：多计时单同刻触发导致弹窗拥挤。
  - 缓解：队列串行展示。
- 风险R4：并发新增导致前端唯一性校验失效。
  - 缓解：后端提交时做最终唯一性校验并返回冲突错误。

回滚策略：
- 移除 `ActiveTimers.vue` 的预警模块与本地缓存 key，恢复当前无提醒行为。
